Glossary 한눈에 보기

Draft 가 PDF·DOCX·HWP 같은 잡다한 파일을 어떻게 일관된 의미 단위로 정리하는지, 그 모든 작업이 어떤 용어로 묶이는지 설명하는 한 페이지짜리 지도.

3분 요약

  1. 1File 은 매니저가 Drive 에 올린 원본 파일 (PDF/DOCX/HWP 등).
  2. 2File 의 본문 텍스트에서 Atom (의미 단위 한 조각) 들을 뽑는다. 12 가지 종류 중 하나로 분류됨.
  3. 3Atom 들 사이를 잇는 Relation (관계) 을 붙인다. 10 가지 종류.
  4. 4모든 Atom 은 Provenance (출처) 를 의무로 가진다. 원본 파일 어디서 왔는지 추적 가능.
  5. 5Atom + Relation = 매니저 워크스페이스의 knowledge graph. 챗봇이 이걸 검색해 답한다.

12 AtomType — 의미 단위의 12 가지 갈래

이름은 EXACT PascalCase 영문. "Req" / "요구사항" 같은 변형 금지 (코드/검색 깨짐).

Requirement

해야 할 일·과업. 과거형/미래형 모두 포함.

예: "지방 거주자 인터뷰 5건 추가"

Deadline

기한·마감일. "~까지" 표현이 명시된 시점.

예: "2026-03-15 까지 제출"

Constraint

제약·자격 요건. 형식/수량/대상 제한.

예: "PDF 10페이지 이내"

Deliverable

산출물. 만들어서 제출하는 결과물.

예: "최종 발표 자료 1부"

Metric

수치·통계. 단위와 함께 의미 있게.

예: "참여 학생 87명"

Narrative

서술·관찰. 패턴이나 분석 한 줄.

예: "지방 거주자가 모바일 결제 빈도 낮음"

Event

특정 시점에 발생한 사건/활동.

예: "3주차 사용성 테스트 진행"

Question

불확실하거나 외부 답이 필요한 사항.

예: "창교에 시니어 명단 공유 가능한지 문의"

Decision

결정·확정 사항. 선택지 중 어느 것.

예: "결제 UX 는 카카오페이 우선"

Reference

외부 문서·조항 인용.

예: "회칙 제6조"

Definition

용어·자격을 명시적으로 정의한 문장.

예: "정회원은 학부 재적생인 자"

Entity

사람·팀·조직. 주체로 등장하는 것 모두.

예: "FLIP 3팀", "LINC 사업단"

색 묶음: 빨강 = 해야 할 것, 보라 = 만들어내는 것, 노랑 = 발생/결정, 회색 = 인용·정의, 초록 = 주체.

10 RelationType — Atom 사이의 관계

두 Atom 을 잇는 방향성 있는 화살표. EXACT 이름만 사용.

관계의미예시
requiresA 가 B 를 필요로 함Requirement → Deliverable
fulfillsA 가 B 를 충족·완료함Deliverable → Requirement
referencesA 가 B 를 참조·인용Requirement → Reference
assigned_toA 가 B 에게 할당됨Requirement → Entity
produced_byA 가 B 에 의해 만들어짐Deliverable → Entity
temporally_afterA 가 B 이후에 발생Event → Event
responds_toA 가 B 에 대한 응답Decision → Question
triggersA 가 B 를 촉발Event → Requirement
approvesA 가 B 를 승인Decision → Deliverable
evolves_toA 가 B 로 진화·갱신Atom → Atom (시계열)

Triple = (Atom A, RelationType, Atom B). 지식의 한 조각이 한 줄. 예: (R1 인터뷰 5건, requires, DL1 시장조사 보고서)

Provenance — 출처 추적의 의무

Provenance 없는 Atom 은 INVALID. 매니저가 항상 원본을 찾아갈 수 있어야 함.

{
  "id": "R1",
  "type": "Requirement",
  "content": "지방 거주자 인터뷰 5건 추가",
  "provenance": {
    "source": {
      "file_id": "uuid-of-FLIP_3팀_2주차_보고서.pdf",
      "location": "section 2 — 진척 현황",
      "raw_text": "지방 거주자 인터뷰 5건을 추가로 진행"
    },
    "extracted_by": {
      "model": "claude-haiku-4-5-20251001",
      "extractor_version": "m6-task-extractor-v1.1",
      "extracted_at": "2026-05-25T12:00:00Z"
    }
  },
  "confidence": 0.8
}

source.file_id

어느 파일에서 왔나

source.raw_text

원문 어느 문장 (80자 이내 발췌)

extracted_by.model

어느 모델이 뽑았나 (재현/디버깅용)

파이프라인 6단계

파일 1개가 들어와서 Atom + Relation 으로 나오기까지.

1

Ingestion

Drive 에서 파일 download → processed_files row 생성.

2

Parsing

PDF/DOCX/XLSX/HWP → plain text. parsed_text 컬럼에 200KB 까지 저장.

3

Classification

파일을 8 카테고리 (공문/사업계획서/실적보고서/회의록 …) 중 하나로 분류.

4

Extraction

LLM (Haiku 4.5, Gemini fallback) 호출 → Atom + Relation 추출. 짧은 JSON 키 (i/t/c/r) 로 출력 토큰 절감.

5

Linking

같은 시리즈/주차 파일들의 Atom 끼리 연결 (evolves_to 관계 등).

6

Validation

schema_compliant + grounded (5-gram fuzzy 매칭) 검증. 통과한 Atom 만 검색 가능.

Chat 가 답하는 방식

매니저 질문 유형에 따라 두 도구를 골라 씀.

정형 질문

search_extracted_atoms

"마감 알려줘", "결정사항", "수치" 같은 분류 가능 질문. AtomType 으로 필터 + keyword 매칭.

빠름, 정확, 토큰 작음.

자유 질문 (RAG)

search_file_contents

"요약해줘", "왜 X 라고 했지", "각 팀 결론" 같은 본문 직접 읽기 필요. query 를 embedding 으로 변환 → file_chunks cosine similarity 검색.

본문 인용 가능, 출처 파일명 명시 의무.

4중 방어선 — Atom 품질 보증

LLM 만 믿지 않음. 4 단계 가드.

① 시스템 프롬프트 (LLM 호출 시)

Glossary v1.1 헤더 주입. AtomType 12개 / RelationType 10개 EXACT 이름 강제.

② Schema 검증 (응답 파싱 후)

JSON 키, AtomType 이름, content 길이, raw_text 존재 확인.

③ Grounding 검증 (raw_text vs 원문)

5-gram fuzzy 매칭 60% 이상. hallucination 차단.

④ 입력 통일 (LLM 호출 전)

50K char 가드, 표/명단 자동 감지 → 모든 행 atom 화 차단.
